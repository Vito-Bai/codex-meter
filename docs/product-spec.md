# Codex 额度监控器产品方案

> 文档状态：立项评审稿  
> 方案版本：v0.2（加入逐轮 token 感知与复盘）  
> 暂定产品名：Codex Meter  
> 目标平台：macOS 14 及以上  
> 产品形态：原生菜单栏应用（独立 `.app`）  
> 编写日期：2026-08-25

## 1. 决策摘要

建议开发一个完全本地运行的 macOS 菜单栏应用，持续展示 Codex 当前额度、每轮对话 token 消耗、重置时间和消耗趋势，并在额度不足或消耗异常时发出提醒。

它本质上是一个独立软件，但采用“菜单栏工具”形态：

- 安装后位于 `/Applications`，像普通 Mac 软件一样启动、更新和卸载。
- 默认不显示 Dock 图标，不创建主窗口，不打断 Codex 工作流。
- 用户通过菜单栏图标查看状态，通过“设置”管理开机启动、提醒阈值、刷新频率和隐私选项。
- 数据优先通过 Codex App Server 的官方结构化接口读取，不读取对话正文，不要求用户粘贴 API Key。
- 第一版保持只读，不自动购买额度、不自动消耗免费重置、不替用户切换模型。

MVP 的核心价值是把“额度余额”和“每轮消耗”连接起来，让用户随时知道四件事：

1. 我还剩多少额度？
2. 什么时候重置？
3. 刚完成的这一轮对话消耗了多少 token，主要消耗在哪里？
4. 按现在的消耗速度，能不能撑到重置？

## 2. 背景与问题

### 2.1 用户问题

Codex 的额度消耗不是按任务数或消息数简单计算。模型、上下文、推理强度、工具调用、检索、缓存和任务运行方式都会影响消耗，因此用户很难凭任务数量建立稳定预期。

目前用户需要主动进入 usage dashboard，或在 Codex CLI 会话中执行 `/status` 才能查看额度。多个任务连续运行时，缺少持续、低打扰的反馈，容易出现两种情况：

- 过度保守：担心额度不足，但实际消耗很少。
- 失去控制：连续运行少数高消耗任务后，才发现额度接近耗尽。
- 难以复盘：不知道具体哪一轮对话消耗较高，也无法识别长上下文、高推理、多工具循环等高消耗模式。

### 2.2 产品机会

将额度状态从“需要主动查询的信息”变成“随时可见的环境信息”，在每轮对话结束后提供即时 token 反馈，并把轮次历史转换成消耗速度、预计耗尽时间和可复盘的使用模式。

## 3. 产品目标与非目标

### 3.1 产品目标

- 让用户在不离开当前工作界面的情况下，2 秒内确认剩余额度和重置时间。
- 让用户在每轮对话结束后立即感知该轮 token 总量及构成。
- 在额度低于安全阈值前主动提醒。
- 展示今日及近 7 日消耗趋势，帮助用户形成用量感知。
- 估算当前用量能否维持到下次重置。
- 支持按轮次定期复盘，识别长上下文、高推理、多次工具循环、低缓存命中等高消耗模式，而不读取任务内容。
- 保持本地优先、低权限、低资源占用。

### 3.2 第一版非目标

- 不承诺把 token 精确换算成套餐额度百分比。
- 不代替 OpenAI 官方账单或 usage dashboard。
- 不读取、索引或上传用户的提示词、代码、文件内容和对话正文。
- 不自动购买 Credits。
- 不自动使用免费额度重置。
- 不自动修改 Codex 模型或推理等级。
- 不做团队管理后台、跨成员配额分配和财务结算。
- 暂不支持 Windows 和 Linux。

## 4. 产品形态

### 4.1 为什么选择菜单栏应用

| 形态 | 优点 | 局限 | 结论 |
| --- | --- | --- | --- |
| macOS 菜单栏应用 | 常驻、低打扰、刷新及时、可发系统通知 | 需要安装独立软件 | 推荐 |
| macOS 桌面 Widget | 一眼可见 | 系统限制刷新频率，桌面被遮挡时不可见 | 可作为后续附加能力 |
| Codex 插件或 Skill | 与 Codex 结合紧密 | 只能在 Codex 内主动调用，无法持续可见 | 不适合作为主形态 |
| 浏览器扩展 | 易打开 Dashboard | 无法覆盖原生 App/CLI 工作流 | 不推荐 |
| Web 页面 | 开发简单 | 需要用户主动打开，无法自然常驻 | 仅适合作为统计详情页 |
| CLI 状态行 | 对 CLI 用户很直接 | 无法覆盖桌面 App，多任务总览较弱 | 作为零开发补充方案 |

### 4.2 软件形态

- 应用名称：Codex Meter（暂定）
- 安装包：签名并公证的 `.dmg`
- 安装位置：`/Applications/Codex Meter.app`
- 运行形态：菜单栏常驻，无 Dock 图标
- 设置入口：菜单栏 → 设置
- 开机启动：用户可选，默认在首次引导中询问
- 更新：内置“检查更新”，后续可支持自动更新
- 退出：菜单栏 → 退出 Codex Meter
- 卸载：退出后将应用移到废纸篓；设置中提供“删除本地历史数据”

### 4.3 首次使用引导

首次启动显示独立原生引导窗口，按“欢迎、连接确认、菜单栏说明、登录启动、配置完成”依次展开。引导只要求用户理解核心价值并完成必要选择，不展示逐轮反馈时长、通知、标题提炼等进阶设置。

菜单栏说明页同时演示三种状态：常态显示 1 周剩余、5 小时额度低于 25% 时切换短周期，以及检测到未读的 OpenAI 官方重置动态时优先显示“官方重置”。用户点击查看动态后，菜单栏恢复常规额度百分比。

完成页说明 Codex Meter 将持续免费提供核心功能，并以弱化入口提供支付宝和微信自愿支持。二维码仅在用户主动选择支付方式后显示，保存在 App 本地，不依赖第三方页面；不预设金额，不付款也不影响任何功能。设置页提供“重新查看使用引导”和“支持开发”入口。

## 5. 核心用户体验

### 5.1 菜单栏状态

默认显示一个环形额度图标和剩余百分比：

```text
◔ 77%
```

可在设置中选择三种显示模式：

- 精简：仅图标，颜色表示健康状态。
- 标准：图标 + 剩余百分比，推荐默认值。
- 完整：图标 + 剩余百分比 + 重置倒计时。

颜色规则：

- 绿色：剩余高于 80%。
- 黄色：剩余 50%–80%。
- 橙色：剩余 25%–50%。
- 红色：剩余低于 25% 或已触达限制。
- 灰色：Codex 未登录、数据不可用或离线。

颜色只作为辅助信息，必须同时提供文本和 VoiceOver 描述。

### 5.2 菜单栏弹窗

点击菜单栏图标后展示：

```text
Codex Meter

额度概览
本周剩余 77% · 还剩 6 天
5 小时剩余 90% · 还剩 4 小时 28 分

本周额度节奏                   本周节奏健康
按当前速度，预计周重置时剩余 31%

刚刚完成的一轮                     59.5K tokens
输入 54.1K · 缓存 43.8K · 输出 369 · 推理 93
[查看本轮详情] [用量复盘]

今日用量                           1.8M tokens
近 7 日                           [迷你趋势图]

可用额外 Credits                  0
免费额度重置                       1 次

[刷新] [打开官方用量页面] [设置]
```

如果存在多个额度桶，分别展示，不将它们错误合并成一个百分比。

### 5.3 每轮对话即时反馈

当 Codex 的一轮对话完成后，Codex Meter 生成一条“轮次用量记录”，并采用低打扰方式提供即时反馈：

- 菜单栏文本临时显示“本轮 59.5K”，默认持续 8 秒，随后恢复为剩余额度。
- 菜单栏弹窗顶部保留最近一轮的总 token 和构成。
- 可选系统通知：“本轮使用 59.5K tokens，约为近 20 轮中位数的 2.1 倍。”
- 多个任务并行完成时按完成时间排队展示，不覆盖尚未读到的高消耗提示。
- 用户可关闭临时菜单栏反馈或修改显示时长；每轮系统通知默认关闭，避免高频打扰。

“一轮对话”定义为一次用户消息触发、以对应 `turnId` 完成或中断为止的完整 Codex turn。一轮中可能包含多次模型请求、工具调用和上下文回传，产品需要聚合该 `turnId` 下的全部 token 更新，不能只展示最后一次模型请求。

默认展示：

- 本轮总 token。
- 输入 token。
- 其中缓存输入 token。
- 输出 token。
- 推理输出 token。
- 相对近 20 轮中位数的倍数。

缓存输入是输入 token 的组成部分，界面不能把两者直接相加。高级详情可进一步展示“非缓存输入 = 输入 token − 缓存输入 token”。

### 5.4 用量复盘

从菜单栏点击“用量复盘”打开独立详情窗口，默认展示近 7 日：

- 每轮 token 柱状图，并区分非缓存输入、缓存输入、输出和推理输出。
- 高消耗轮次榜单与异常值标记。
- 按模型、推理等级、对话时长、上下文占用和工具循环次数聚合。
- 与个人历史基线比较，例如“高于近 20 轮中位数 110%”。
- 只基于元数据生成的可能原因，例如“长上下文重复回传”“推理输出较高”“工具循环较多”或“缓存命中偏低”。
- 支持给轮次添加本地标签或备注，帮助用户验证自己的使用假设。

产品不把“高消耗”直接等同于“低效率”。复盘视图只呈现事实和相关性，是否值得由用户结合任务价值判断。

### 5.5 系统通知

默认提醒：

- 剩余 25%。
- 剩余 10%。
- 预计会在重置前耗尽。
- 已触达额度限制。
- 数据源连续 30 分钟不可用。

可选提醒：

- 剩余 50%。
- 单轮 token 高于近 20 轮中位数的指定倍数。
- 单个任务结束后额度下降超过用户设置值。
- 每日用量摘要。
- 额度重置完成。

同一阈值在同一个额度窗口内只提醒一次，避免重复打扰。

## 6. 功能需求

### 6.1 P0：MVP 必须具备

#### A. 当前额度

- 展示已用百分比、剩余百分比。
- 展示额度窗口长度和下次重置时间。
- 支持官方返回的多个额度桶。
- 展示套餐类型、Credits 状态和是否触达限制。
- 在存在免费额度重置时显示数量和有效期，但第一版不提供“立即使用”按钮。

#### B. 每轮对话 token 感知

- 订阅当前活跃线程的 token 用量更新，并按 `threadId`、`turnId` 聚合。
- 在 `turn/completed`、`interrupted` 或 `failed` 后形成一条完整轮次记录。
- 展示本轮总 token、输入、缓存输入、输出和推理输出。
- 菜单栏临时展示本轮总量，默认 8 秒后恢复剩余额度。
- 菜单栏弹窗保留最近 10 轮的用量摘要。
- 以近 20 轮中位数为个人基线，标记 1.5 倍、2 倍等异常轮次。
- 对中断和失败轮次照常记录消耗，并明确标记结果状态。
- 支持关闭轮次记录；关闭后不在本地保存历史，但当前会话内仍可显示即时值。

#### C. 用量复盘与趋势

- 展示今日 token 活动量。
- 展示近 7 日每日 token 趋势。
- 展示近 7/30 日的逐轮 token 趋势和高消耗轮次。
- 按模型、推理等级、轮次状态、上下文占用和工具循环次数聚合。
- 根据 token 构成与运行元数据生成“可能的高消耗因素”，不读取提示词、回答、代码或工具内容。
- 支持给轮次添加仅保存在本地的标签和备注。
- 本地保留额度百分比快照，用于计算周期内变化曲线。
- 支持切换近 24 小时、7 日和当前额度周期。

#### D. 消耗预测

- 基于近 6 小时、24 小时和本周期的额度变化估算消耗速度。
- 给出“预计撑到重置”或“预计在某时耗尽”。
- 样本不足时明确显示“数据不足”，不输出伪精确预测。
- 预测只作为本地估算，不标记为官方结果。

#### E. 通知与阈值

- 默认在剩余 25% 和 10% 时提醒，并支持 50% 和自定义阈值。
- 支持单轮 token 异常提醒，默认关闭。
- 支持预计耗尽提醒。
- 支持免打扰时间段。
- 记录本周期已发送通知，避免重复。

#### F. 状态与错误处理

- Codex 未安装：给出安装或打开官方页面的引导。
- Codex 未登录：引导用户打开 Codex 完成登录。
- API Key 模式：说明 ChatGPT 套餐额度数据不可用，避免与 API 计费混淆。
- 网络断开：保留最近一次数据，并展示更新时间。
- Codex 升级导致协议变化：降级读取最近本地快照并提示更新 Codex Meter。

### 6.2 P1：增强版

#### A. 跨任务深度分析

- 在任务开始和结束时记录额度快照。
- 将轮次聚合为线程和项目维度，展示每个任务的总 token 与轮次分布。
- 展示“最近高消耗任务”，仅使用任务标题或用户可选的匿名编号。
- 提供隐私模式：完全不记录任务标题，只记录时间和用量。

注意：官方额度百分比可能按整数更新，单任务额度变化可能显示为 `<1%`，不能据此承诺小数级精度。

#### B. 用量建议

- 根据剩余额度和重置倒计时给出建议，例如：
  - “当前节奏可维持到重置。”
  - “建议将常规任务切换至更轻量模型。”
  - “建议拆分长任务并减少无关上下文。”
- 建议只做提示，不自动修改 Codex 设置。

#### C. 导出

- 导出 CSV：时间、额度桶、已用百分比、token 数、任务匿名 ID。
- 导出诊断包：版本和错误日志，不包含鉴权信息及对话内容。

### 6.3 P2：未来能力

- macOS 桌面 Widget，展示最近一次同步状态。
- iPhone 或 Apple Watch 只读查看。
- 团队工作区额度看板。
- 经用户二次确认后使用免费额度重置。
- 与 Codex 联动，在新建任务时提示更节省额度的模型选择。

## 7. 设置与软件管理

### 7.1 常规设置

- 登录时自动启动。
- 显示或隐藏 Dock 图标。
- 菜单栏显示模式。
- 每轮结束后的菜单栏 token 反馈：开启/关闭，显示 3/5/8/15 秒。
- 自动刷新频率：实时事件 + 1/5/15 分钟兜底轮询。
- 时间格式与语言。
- 启动后是否自动检查更新。

### 7.2 提醒设置

- 启用额度阈值提醒。
- 自定义提醒百分比。
- 启用预计耗尽提醒。
- 启用单轮高消耗提醒，并设置相对个人基线的倍数。
- 启用每日摘要。
- 设置免打扰时间。

### 7.3 隐私与数据设置

- 是否记录历史额度快照。
- 是否记录逐轮 token 元数据，默认开启。
- 历史保留期：7/30/90 天或永久。
- 是否记录任务标题，默认关闭。
- 是否保存用户为轮次添加的本地标签和备注。
- 导出本地数据。
- 一键删除所有本地历史。
- 展示本地数据库实际路径和占用空间。

### 7.4 关于与维护

- Codex Meter 版本。
- 检测到的 Codex 版本。
- 当前数据源与最近同步时间。
- 检查更新。
- 打开诊断信息。
- 打开官方 Codex usage dashboard。
- 退出应用。

## 8. 首次使用流程

1. 用户将 Codex Meter 拖入 Applications 并启动。
2. 应用检测 Codex CLI/App Server 是否可用。
3. 应用说明读取范围：“只读取额度与 token 元数据，不读取对话正文或代码内容。”
4. 用户选择是否开机启动。
5. 用户选择是否允许系统通知。
6. 成功读取额度后展示当前剩余百分比和重置时间，并说明每轮结束后会显示 token 消耗。
7. 如果读取失败，按“未安装、未登录、API Key 模式、网络错误、版本不兼容”分别给出处理建议。

首次使用不要求用户输入 OpenAI 密码、访问令牌或 API Key。

## 9. 数据与技术方案

### 9.1 推荐技术栈

- Swift 6
- SwiftUI
- `MenuBarExtra` 构建菜单栏交互
- UserNotifications 提供系统通知
- ServiceManagement 管理开机启动
- SQLite 或 SwiftData 保存本地快照
- Sparkle 或自建签名更新源提供后续自动更新

选择原生 Swift 的原因：启动快、内存占用低、系统集成自然，并且无需携带 Electron/Node 运行时。

### 9.2 数据源

优先数据源：Codex App Server。

- `account/rateLimits/read`：当前额度窗口、已用百分比、重置时间、套餐、Credits、限制状态。
- `account/rateLimits/updated`：额度发生变化时的实时通知。
- `account/usage/read`：账户 token 汇总和每日 buckets。
- `account/usage/read` + `threadId`：支持时读取线程级估算用量。
- `thread/tokenUsage/updated`：活跃线程的 token 更新，包含 `threadId`、`turnId`、本次和线程累计 token 构成。
- `turn/completed`：确定一轮对话完成、中断或失败，并固化该轮聚合结果。

官方说明中，App Server 是 Codex 用于构建富客户端的接口；额度接口直接返回 `usedPercent`、窗口长度和 `resetsAt`，并提供活跃线程的 `thread/tokenUsage/updated` 事件。Token 用量接口需要 Codex 服务支持的登录方式，API-key-only 与 Bedrock 模式不支持账户级 ChatGPT 用量数据。

参考：

- [Codex App Server](https://learn.chatgpt.com/docs/app-server)
- [Codex 定价与用量说明](https://learn.chatgpt.com/docs/pricing)

```text
│        Codex Meter.app       │
├──────────────┬───────────────┤
│ 菜单栏与设置 │ 通知与预测引擎 │
├──────────────┴───────────────┤

├──────────────┬───────────────┤

│ 读取/订阅    │ 轮次/趋势/去重 │
└──────┬───────┴───────────────┘
       │ 本机进程通信
┌──────▼───────────────────────┐
│       Codex App Server       │
└──────────────┬───────────────┘
               │ Codex 已登录会话
          OpenAI Codex 服务
```

### 9.4 连接策略

额度读取和逐轮 token 监听采用双通道设计：

#### A. 账户额度通道

- Codex Meter 启动独立的只读 App Server 子进程。
- 使用用户现有的 Codex 登录状态，通过标准输入输出进行本机 JSON-RPC 通信。
- 每次启动先读取完整额度与账户 token 历史，再订阅额度更新。
- 应用退出时正常终止子进程，崩溃后采用指数退避重启。
- 即使 Codex Desktop 没有打开，账户额度监控仍可工作。

#### B. 逐轮 token 通道

`thread/tokenUsage/updated` 只针对相应 App Server 已加载和订阅的活跃线程。独立子进程不能被假设为天然收到另一个 Codex Desktop 进程的全部 turn 事件，因此 MVP 必须在技术验证阶段确定以下采集顺序：

1. 优先连接 Codex 的共享 App Server daemon，并订阅已加载线程的 turn 与 token 事件。
2. 如果当前 Codex 版本不允许安全复用共享连接，则使用只读“本地会话元数据适配器”，从 Codex rollout 事件中提取轮次边界和 token 计数，明确跳过消息正文、工具参数和工具输出字段。
3. 若两种通道同时可用，以 App Server 事件为主，并用本地累计值做去重和完整性校验。
4. 如果某个外部或远程任务没有在本机留下可观察事件，将其标记为“无逐轮明细”，但账户总额度仍正常更新。

逐轮监听是阶段 0 的关键技术门槛：没有验证覆盖 Codex Desktop、CLI 和并行任务之前，不能宣称“所有轮次均可追踪”。

### 9.5 本地数据模型

建议保存以下最小字段：

- 采样时间。
- `limitId` 与可选名称。
- 已用百分比。
- 窗口长度。
- 重置时间。
- Credits 余额和限制状态。
- 每日 token 数。
- 轮次 ID 的本地哈希、线程 ID 的本地哈希和轮次状态。
- 每轮输入、缓存输入、输出、推理输出和总 token。
- 模型、推理等级、持续时间、上下文占用和工具调用次数等非内容元数据。
- 可选的用户本地标签与备注。
- 数据源版本和 Codex 版本。

默认不保存：

- 提示词。
- 模型回答。
- 工具调用参数或输出。
- 用户代码和文件内容。
- OpenAI 访问令牌。

### 9.6 轮次 token 聚合逻辑

App Server 的 `thread/tokenUsage/updated` 事件包含 `threadId`、`turnId`，以及 `last` 和 `total` 两组 token 明细。Codex Meter 以 `turnId` 为核算单元：

1. 收到某个 turn 的第一条 token 更新时创建内存聚合记录。
2. 将该 turn 后续更新中的 `last` 用量累计，或用线程累计值做差分校验。
3. 收到 `turn/completed` 后固化该轮记录；中断和失败也固化，但标记对应状态。
4. 对重复事件使用事件序列和累计值去重，避免进程重连后重复计算。
5. 如果事件丢失或数据无法一致校验，将该轮标记为“估算”或“不完整”，不显示伪精确结果。

一轮的 token 构成包括：

- `inputTokens`：该轮所有模型请求处理的输入总量，可能包含重复传递的对话上下文。
- `cachedInputTokens`：输入 token 中命中缓存的部分，不应与输入 token 再次相加。
- `outputTokens`：模型输出 token。
- `reasoningOutputTokens`：推理输出 token。
- `totalTokens`：官方事件返回的本次总量，作为主展示值。

复盘视图还可以计算缓存命中率、非缓存输入量、输入/输出比例和单轮工具循环次数，但必须标注这些是诊断指标，不是套餐额度的直接换算公式。

Token 数反映模型处理量，不等于套餐额度扣减值。模型、推理等级、工具和缓存计价权重不同，因此产品必须把“本轮 token”与“额度百分比变化”并列展示，不能用一个固定比例互相换算。

## 10. 预测逻辑

### 10.1 基本算法

对当前额度窗口内的百分比快照做稳健线性估计：

```text
消耗速度 = 有效时间段内已用百分比变化 / 时间
预计重置时已用 = 当前已用 + 消耗速度 × 距重置时间
预计耗尽时间 = 当前时间 + 剩余百分比 / 消耗速度
```

### 10.2 防误导规则

- 采样跨度少于 2 小时或有效变化少于 2 个百分点时，不给出耗尽时间。
- 重置发生后自动开始新窗口，旧窗口不参与当前预测。
- 对瞬时高消耗采用短期和长期两条速度线，不只使用最近一个任务。
- 百分比长时间不变时显示“近期消耗较低”，不宣称零消耗。
- 明确区分“官方返回”和“本地估算”。

## 11. 隐私与安全

### 11.1 原则

- Local-first：历史和设置仅保存在本机。
- Least privilege：不申请辅助功能、屏幕录制、通讯录或完整磁盘访问权限。
- No credential handling：不读取或复制 `auth.json`，不保存 OpenAI token。
- Read-only by default：第一版不调用会改变账户状态的接口。
- No analytics by default：不上传产品使用分析；若未来加入，必须明确选择加入。

### 11.2 潜在风险

- App Server 是随 Codex 版本演进的接口，字段可能发生兼容性变化。
- 启动子进程会继承必要的本机环境，必须限制日志，不输出环境变量和鉴权信息。
- 额度与 token 是敏感的个人使用数据，导出文件应由用户主动创建。

### 11.3 应对措施

- 使用 App Server 生成的协议类型或固定版本适配层。
- 对未知字段宽容解析，对必需字段缺失进行明确降级。
- 日志白名单化，只记录错误码、版本和状态，不记录原始响应全文。
- 应用签名、公证，并提供可验证的更新签名。

## 12. 性能要求

- 空闲内存目标：低于 80 MB。
- 空闲 CPU：平均低于 0.5%。
- 冷启动到展示最近状态：低于 1 秒。
- 在线获取新状态：通常低于 3 秒。
- 本地数据库 90 天预计低于 20 MB。
- 后台轮询默认不高于每分钟一次；优先依靠更新事件。

## 13. 兼容性与降级

| 场景 | 产品行为 |
| --- | --- |
| ChatGPT 登录模式 | 完整显示额度和 token 历史 |
| API Key 模式 | 显示“套餐额度不可用”；后续可单独支持 API Usage API |
| Codex 未启动 | Codex Meter 自行启动只读 App Server |
| Codex 未安装 | 引导安装 Codex |
| 网络离线 | 展示最近快照及最后更新时间 |
| 接口暂时失败 | 自动退避重试，不弹出高频通知 |
| 协议不兼容 | 展示基础缓存状态并提示升级 |
| 多额度桶 | 独立展示每个额度桶 |
| 官方百分比未变化 | token 趋势继续更新，额度显示保持不变 |

## 14. 成功指标

个人版 MVP 以可用性而非增长为主：

- 额度读取成功率不低于 99%。
- 当前状态与官方 usage dashboard 基本一致。
- 活跃线程每轮结束后能在 3 秒内显示该轮总 token 及构成。
- 同一轮发生多次模型调用和工具循环时，轮次总量不会只取最后一次更新，也不会重复累计。
- 阈值通知不重复、不漏掉已观察到的阈值跨越。
- 菜单栏查询路径不超过一次点击。
- 连续运行 7 天无明显内存增长。
- 不采集或泄露任务正文和鉴权信息。

如果未来公开发布，可增加匿名、用户主动选择加入的指标：安装成功率、日活、通知点击率和崩溃率。

## 15. MVP 验收标准

满足以下条件即可认为第一版可交付：

1. 在支持的 ChatGPT 登录模式下，能够显示套餐、已用/剩余百分比、重置时间和 Credits 状态。
2. 菜单栏颜色和文案随剩余额度变化。
3. 每轮对话结束后，菜单栏能显示本轮总 token，并在详情中展示输入、缓存输入、输出和推理输出。
4. 一轮中存在多次模型请求时，能够按 `turnId` 正确聚合；中断和失败轮次也能记录并标记状态。
5. 能保存并展示至少 7 日逐轮 token 趋势、每日趋势和额度快照。
6. 用量复盘能展示高消耗轮次、个人基线比较和至少三类不依赖内容的可能消耗因素。
7. 25%、10%、预计耗尽和可选单轮高消耗通知可以配置，并正确去重。
8. 离线、未登录、Codex 未安装和协议失败均有明确状态。
9. 开机启动、退出、检查更新和删除本地数据均可由用户管理。
10. 不读取对话正文、不保存鉴权 token、不申请无关系统权限。
11. 应用经过签名和公证，可通过 `.dmg` 正常安装。
12. 在目标 macOS 版本上连续运行 7 天无阻断性问题。

## 16. 开发计划

### 阶段 0：技术验证，2–3 天

- Swift 与 App Server 建立连接。
- 完成 initialize、额度读取、`thread/tokenUsage/updated` 和 turn 生命周期事件接收。
- 验证单轮多次模型请求的聚合与去重逻辑。
- 验证 Codex Desktop、CLI 和至少两个并行任务的逐轮事件覆盖。
- 验证共享 daemon 连接方案；如果不可用，验证只读本地会话元数据适配器。
- 验证 App Server 子进程生命周期。
- 验证未登录、离线和 API Key 模式。
- 固化一组脱敏协议样例作为测试数据。

退出条件：能在独立 Swift 原型中稳定读取当前额度，并正确核算一轮包含多次模型请求的 token 总量。

### 阶段 1：MVP 开发，8–12 个工作日

- 菜单栏 UI。
- 当前额度与重置倒计时。
- 每轮 token 即时反馈与最近轮次列表。
- 本地快照、逐轮复盘和 7 日趋势。
- 阈值通知。
- 设置、开机启动和基础诊断。
- 错误状态与自动重连。

### 阶段 2：测试与打包，3–5 个工作日

- 单元测试和协议兼容测试。
- 长时间运行测试。
- 性能与隐私检查。
- 应用签名、公证和 DMG。
- 更新机制与发布说明。

预计首个可安装 MVP：约 3–4 周；如果先只做个人自用、不做公证和自动更新，可在约 1–2 周内提供第一版。新增时间主要用于跨进程轮次采集、聚合校验和复盘视图。

### 阶段 3：增强版，按反馈排期

- 跨任务和项目维度的深度分析。
- 更可靠的消耗预测。
- 用量建议。
- CSV 导出。
- 可选桌面 Widget。

## 17. 主要风险与取舍

### 风险 1：接口随 Codex 升级变化

结论：可接受，但需要兼容层和自动化协议测试。App Server 比解析本地日志可靠得多，也更符合产品化方向。

### 风险 2：跨 Codex 客户端的逐轮事件覆盖不完整

结论：账户额度可以由独立 App Server 稳定读取，但逐轮事件可能属于另一个 Desktop/CLI 进程。阶段 0 必须验证共享 daemon 订阅；必要时使用只读本地会话元数据适配器作为降级，并在 UI 中展示采集覆盖状态。

### 风险 3：额度百分比精度不足

结论：MVP 不展示虚假的小数百分比。用官方百分比回答“还剩多少”，用 token 与本地趋势回答“最近为什么用得快”。

### 风险 4：用户把套餐额度与 API 账单混淆

结论：界面明确标注“ChatGPT/Codex 套餐额度”。API Key 模式单独处理，未来若支持 API Usage API，应作为另一个数据卡片展示。

### 风险 5：功能过度扩张

结论：第一版坚持只读监控。购买额度、使用重置、自动改模型都需要更强的授权与防误操作设计，不进入 MVP。

## 19. 推荐结论

建议批准开发 MVP，定位为“Codex 套餐额度与逐轮消耗的本地菜单栏仪表盘”，并遵循四条边界：

1. 额度状态采用官方 App Server 数据。
2. 每轮 token 按官方 turn 标识聚合，异常或缺失数据明确标注。
3. 趋势和预测明确标注为本地估算。
4. 第一版只读、无凭证托管、无任务正文采集。

这能以较低工程风险解决当前最核心的问题，同时为任务级分析和更细致的用量管控保留扩展空间。
